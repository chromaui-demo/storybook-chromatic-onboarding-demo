## Customer brief

You are meeting Trailhead Travel's design-system lead, frontend platform engineer, and engineering
manager.

- The design system is React, but product teams also use Next.js, Angular, Web Components, and React
  Native Web.
- Storybook exists in pockets with inconsistent stories and duplicated configuration.
- Pull requests rely on manual screenshots and reviewers often miss responsive regressions.
- Several components call unstable development APIs, making tests flaky.
- Accessibility issues are found during release hardening.
- Leadership wants faster review without creating a test suite nobody trusts.

For the postsales track, assume the design-system Storybook and a passing `main` baseline already
exist. Only happy paths are consistently covered, some teams still approve screenshots in chat, and
CI is not required across every owning team.

The customer has 20 minutes. Reserve at least two minutes for discovery and three minutes for questions.

## Discovery prompts

Ask enough to choose a relevant demo path:

1. Which team owns component quality and Storybook configuration today?
2. Is the immediate priority development, documentation, testing, review, or cross-team discovery?
3. Which frameworks need independent ownership and deployment?
4. How are intentional visual changes approved today?
5. What makes current CI slow or unreliable?
6. What accessibility policy or release gate already exists?
7. If Chromatic is already in place, where does evidence or review still leave the workflow?

The reviewer will answer with two priorities. Adapt the demo to those answers.

## Required evidence

Show these items as one workflow, not six disconnected features:

1. A React component expressed as editable, documented story states.
2. Deterministic success/error data through MSW.
3. One interaction test and one accessibility result.
4. A Chromatic visual diff with a correct baseline explanation.
5. A CI/branch result and the review decision needed to move forward.
6. A recommendation that matches the track:
   - **Presales:** a bounded evaluation, named owner, and proof of success.
   - **Postsales:** a specific coverage gap, smallest useful change, and measurement.

Composition, modes, MCP, and TurboSnap are optional demo moments. Include them only when discovery makes
them relevant.

## Recovery moment

The reviewer chooses one interruption:

- a denied visual regression;
- an interaction test that never reaches its expected state;
- an MSW request that escapes to the network;
- a composed Storybook reference that is unavailable;
- a TurboSnap result that retests more stories than expected;
- a question about Storybook 11 or unsupported framework AI behavior.

Diagnose aloud. State the evidence you would inspect, what you know, what remains unknown, and the
safest next action. You do not need to repair an issue live if the repair would derail the call.

## Scoring rubric

Score each dimension from 1–4. A passing capstone has no score below 2 and a total of at least 18/24.

| Dimension                | 1: Needs work                             | 2: Developing                     | 3: Ready                                               | 4: Strong                                                     |
| :----------------------- | :---------------------------------------- | :-------------------------------- | :----------------------------------------------------- | :------------------------------------------------------------ |
| Discovery                | Starts a fixed feature tour               | Asks questions but barely adapts  | Reflects priorities and adapts                         | Surfaces constraints and reframes the path insightfully       |
| Storybook fluency        | Cannot connect story/config/test concepts | Operates the happy path with help | Explains and operates the core workflow                | Connects architecture and tradeoffs clearly                   |
| Chromatic fluency        | Misstates baselines or review             | Completes review with prompting   | Explains branch, baseline, tests, and review correctly | Anticipates ancestry, CI, and adoption risks                  |
| Technical recovery       | Guesses or hides the failure              | Identifies a plausible check      | Uses evidence and chooses a safe next step             | Diagnoses systematically while preserving customer confidence |
| Customer communication   | Jargon-heavy feature list                 | Some outcome language             | Concise narrative tied to stated needs                 | Teaches complex boundaries simply and honestly                |
| Value and recommendation | No next step or pushes more usage         | Broad next step                   | Ties a measured next step to a real gap                | Balances value, risk, ownership, boundaries, and expansion    |

## Feedback format

The reviewer provides:

- one moment to keep;
- one explanation to tighten;
- one technical topic to revisit;
- one recommended next practice call;
- the rubric score with brief evidence.

The SE records that feedback in `progress/<handle>.md` and names an owner and date for the follow-up.
