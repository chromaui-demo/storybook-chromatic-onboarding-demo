## Shared customer brief

You are meeting Trailhead Travel's design-system lead, frontend platform engineer, and engineering
manager.

- The design system uses React. Product teams also use Next.js, Angular, Web Components, and React
  Native Web.
- Storybook exists in pockets with inconsistent stories and duplicated configuration.
- Pull requests rely on manual screenshots and reviewers miss responsive regressions.
- Component behavior tests and examples drift apart.
- Leadership wants faster review without creating a suite the teams do not trust.

During core onboarding, Trailhead is deciding whether to upgrade and pilot the current Storybook
workflow. During technical training, assume the React Storybook and a passing Chromatic baseline
already exist, but adoption is uneven.

## Core onboarding conversation

### The purpose

Help the customer make a sound evaluation decision. Use the prepared demo project and your own words.
Do not live-code or diagnose a seeded technical failure.

  <strong>This is practice, not a script recital</strong>
  <div>
    The goal is to connect product knowledge to the customer's situation. Ask

### Required proof

Show these moments as one customer story:

1. **Storybook 10:** Explain the platform value, ESM or runtime boundary, and safe evaluation plan.
2. **Useful stories:** Show the prepared component states that represent the customer's risk.
3. **Storybook MCP:** Prove that the agent inspected documented component context before proposing UI.
4. **Storybook Test locally:** Run one browser test beside the rendered component.
5. **Storybook Test in CI:** Show the same proof attached to a pull request or prepared CI run.
6. **Chromatic:** Show one visual comparison and the review decision.
7. **Evaluation close:** Name the scope, owner, success evidence, and finish line.

State the current MCP preview and React-only docs-tool boundary. Distinguish Storybook Test from
Chromatic visual tests.

### Questions to think through

- What decision is Trailhead trying to make?
- Which proof best addresses its current constraint?
- Which feature would you leave out of this conversation?
- Where might you need to slow down and define a technical term?
- Which boundary would make your recommendation more trustworthy?

### Demo continuity

If an external page fails, use prepared backup evidence and continue. Environment troubleshooting is
not part of core onboarding.

## Post-sales technical assessment

### The assignment

Find a consequential adoption or coverage gap. Operate the workflow, diagnose one seeded problem, and
recommend the smallest change that improves the customer's evidence.

### Discovery prompts

Ask enough to choose a relevant implementation path:

1. Which team owns Storybook configuration and component quality today?
2. Where do local tests, CI checks, or review still depend on memory?
3. Which important states are missing or unreliable?
4. How are visual changes approved?
5. Which framework and repository boundaries affect ownership?
6. What would prove that the adoption change helped?

The reviewer answers with two priorities. Adapt the call to those answers.

### Required proof

Show the evidence relevant to the adoption gap. The call must include:

1. the current Storybook 10 platform and upgrade status;
2. one grounded Storybook MCP workflow or a clear reason it does not fit;
3. one Storybook Test result locally and in CI;
4. one Chromatic build, baseline, or review decision;
5. the ownership and policy needed to sustain the change;
6. a specific adoption recommendation and measurement.

Modes, composition, MSW, and TurboSnap are optional. Use them only when discovery makes them relevant.

### Recovery moment

The reviewer chooses one interruption:

- a Storybook Test that fails only in CI;
- an interaction test that never reaches its expected state;
- an MSW request that escapes to the network;
- a denied visual regression;
- an unavailable composed Storybook;
- a TurboSnap result that retests more stories than expected.

Diagnose aloud. State what you know, what remains unknown, which evidence you will inspect, and the
safest next action. You do not need to finish a long repair during the call.

### Technical readiness rubric

Score each dimension from 1–4. A passing capstone has no score below 2 and a total of at least 18/24.

## Feedback format

The reviewer provides:

- one moment to keep;
- one explanation to tighten;
- one product boundary to clarify;
- one next practice for the learner;
- the track-specific rubric score with brief evidence.

Keep the feedback in the system that supports your development: Notion, Obsidian, Linear, a document,
or your team's learning platform. Add an owner and date only when the feedback needs follow-up.
