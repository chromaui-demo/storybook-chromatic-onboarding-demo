## What you are learning

- How to lead with customer context instead of a product tour.
- How to answer questions without hiding important boundaries.
- How to use evidence without narrating implementation details.
- How to turn interest into a focused evaluation.

## Validate the demo project

Before the call:

```sh
pnpm check
pnpm test:storybook
pnpm dev
```

Open every story, test, CI result, and Chromatic build in advance. Confirm that Codex can reach the
Storybook MCP server. Keep backup evidence for any hosted service.

## Lead the conversation

1. Confirm the customer decision and current constraint.
2. Explain why Storybook 10 is the platform step and state the migration boundary.
3. Show Storybook MCP using documented component context.
4. Run one Storybook Test locally and connect it to the CI result.
5. Show one Chromatic visual change and the review decision.
6. State the boundary of each capability.
7. Close with a bounded evaluation, named owner, and measurable finish line.

Core onboarding does not test technical recovery. If a hosted page fails, use backup evidence and keep
the conversation moving. Technical diagnosis belongs in post-sales technical training.

## Questions to think through

- Did you confirm the customer's problem before opening the product?
- Which explanation made the value clear?
- Which moment became more technical than the customer needed?
- Did you state the MCP preview and testing boundaries plainly?
- Did the proposed evaluation have a clear scope, owner, and finish line?

## How would you respond?

Practice these customer questions without using a prepared script:

- “Why should we upgrade if Storybook already works?”
- “Why does an agent need MCP if it can read our repository?”
- “What does Storybook Test add to our existing test suite?”
- “Why run the same test locally and in CI?”
- “Does accepting a Chromatic change mean the design is correct?”

For each answer, connect the problem, mechanism, proof, value, and boundary.

## Ask for focused feedback

The reviewer records:

- one explanation that made the value clear;
- one moment that became too technical;
- one claim or boundary that needs correction;
- one demo step to remove;
- whether the proposed evaluation has a clear owner and finish line.

## Complete core onboarding

Core onboarding is complete when:

- the demo project passes the repository and Storybook tests;
- all external evidence has a working link or backup;
- a teammate gives feedback on the conversation;
- the evaluation close names scope, owner, proof, and finish line;
- no secret or generated build output is committed.

Keep the feedback wherever it will help you prepare for a real customer conversation. There is no
required progress file. Share a link only if your team uses one for onboarding check-ins.
