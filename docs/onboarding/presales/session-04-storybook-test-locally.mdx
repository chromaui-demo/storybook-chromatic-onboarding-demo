## Teach the reuse, not the runner

Storybook Test uses the Vitest addon to turn stories into browser tests. A story can provide several
levels of proof:

- **Render test:** The story renders without an error.
- **Interaction test:** A play function drives the UI and checks visible behavior.
- **Accessibility test:** Automated checks find common accessibility violations in the rendered state.

The value is one maintained state that a developer can see, run, debug, and automate. The team does not
need a separate fixture for every tool.

Read the current [Storybook testing overview](https://storybook.js.org/docs/writing-tests) before the
session.

## See the fast local loop

Open the React Storybook at `http://localhost:6007`.

1. Open **Reservation interaction**.
2. Run the story test from the testing widget.
3. Replay the interaction steps.
4. Point to the visible assertion and final state.
5. Turn on watch mode and explain that related tests rerun after a change.

Then run the same project from the terminal:

```sh
pnpm --filter @demo/react test:storybook
```

The UI is the teaching and debugging surface. The command is the automation surface. They run the same
story-defined behavior.

## Make one failure useful

Use Codex to make a temporary, reversible assertion change in the interaction story. Run the test and
show:

- which story failed;
- which step failed;
- what the browser rendered;
- how the failure links back to the visible story.

Restore the correct assertion and rerun the test. Do not leave the branch failing.

Storybook Test complements application tests. It does not replace every test layer.

## Questions to think through

- Which customer-visible behavior deserves an interaction test?
- What can the Storybook UI show that a terminal failure cannot?
- When is a render test enough?
- Which workflow still needs an application-level end-to-end test?
- How would you explain the difference between functional and visual proof?

## How would you respond?

> “We already run unit and end-to-end tests. Is Storybook Test just another test suite to maintain?”

Explain the loop without opening the source file:

> The story already describes the state. Storybook Test runs that state in a real browser, drives the
> interaction, shows the result beside the component, and reruns the relevant test while the developer
> works.

Then state what moves to CI in the next session: the same proof, run for every pull request.
