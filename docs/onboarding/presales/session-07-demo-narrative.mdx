## What you are learning

- How to make several product capabilities feel like one workflow.
- How to choose demo moments based on one customer decision.
- How to state value and boundaries without turning the session into a feature tour.
- How to close with a practical next step.

## Use one teaching pattern for every feature

For each feature, state:

1. **Problem:** What goes wrong today?
2. **Mechanism:** What does the feature do?
3. **Proof:** What can the customer see in the demo?
4. **Value:** What changes for the team?
5. **Boundary:** What does the feature not solve?

If a demo moment cannot answer all five, tighten it or remove it.

## Questions to think through

- What decision should the customer be ready to make at the end?
- Which demo moment is essential to that decision?
- Which feature is interesting but unnecessary for this customer?
- Where could your explanation become too technical?
- What honest boundary will increase trust?
- What is the smallest useful evaluation the customer could run next?

## Prepare the demo project

Before rehearsal:

```sh
pnpm check
pnpm test:storybook
pnpm dev
```

Confirm:

- the three story links open;
- the MCP server is connected;
- the local Storybook test passes;
- the prepared CI result is available;
- the Chromatic build opens without a permission request;
- no secret appears in the repository or presenter notes.

Keep a screenshot or recording for any external page that could be unavailable during the call.

## Remove technical drag

Delete a step when it exists only to prove that you know a command. Keep technical detail when it helps
the customer understand a constraint, trust the evidence, or define the evaluation.

Do not live-code in the capstone unless the customer decision requires it. The project should be ready
before the call.

## How would you respond?

> “This all looks useful, but what should our team actually try first?”

Close with:

End with:

- the repository or component scope;
- the customer owner;
- the three proofs to collect;
- the date or event that ends the evaluation;
- the decision the evidence will support.

Example:

> Trailhead will upgrade one React Storybook, connect its documented components to Codex, and run the
> ReservationCard stories through Storybook Test in CI. The platform lead owns the evaluation. It ends
> when the static build, grounded agent task, and pull-request tests pass on the pilot branch.
