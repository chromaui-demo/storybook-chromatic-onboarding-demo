## Learner access

Confirm every SE has:

- an approved computer with permission to install VS Code, Git, Node.js, pnpm, and Codex;
- a ChatGPT account with Codex access;
- read and write access to the GitHub repository;
- access to the support channel.

Core onboarding can use a read-only Chromatic project and prepared CI evidence. Learners do not need a
project token or permission to accept baselines. Post-sales technical training needs the approved
secret manager, the training project, and the least role required for the implementation work.

## Repository readiness

1. Publish this repository with a protected `main` branch and a passing initial commit.
2. Run `pnpm test:onboarding:setup` on Node 20 to test a clean clone, install, branch, checks, Hub, and React Storybook.
3. Confirm that `pnpm test:storybook` passes and that `.github/workflows/storybook-test.yml` runs on a
   pull request.
4. Decide whether SEs may merge course branches or whether branches remain disposable.
5. Give technical-training learners write access and reserve the `onboarding/<handle>` branch namespace.

The checked-in repository already pins Storybook 10.5.5. Day 1 therefore performs a real upgrade
health check and migration review, but the upgrade command should be a no-op. If a cohort must perform
a live Storybook 9-to-10 migration, maintain a tested `course/storybook-9-start` tag separately and
have technical-training learners branch from that tag. Core onboarding should explore the upgrade from
the working Storybook 10 project. Do not downgrade shared `main` during a cohort.

## Core onboarding learning environment

Prepare these assets before Session 1:

1. A working React Storybook 10 project with the ReservationCard stories.
2. A connected Storybook MCP endpoint and one verified read-only prompt.
3. A passing local Storybook Test result and one safe failure example.
4. A passing pull request run from `.github/workflows/storybook-test.yml`.
5. A Chromatic branch build with one clear visual change and recorded decision.
6. Backup screenshots or recordings for every hosted surface.

Do not turn core onboarding into an access exercise. Pair on installation and provide prepared hosted
evidence. Focus feedback on customer understanding, thoughtful questions, clear explanations, and
honest boundaries.

## Shared Chromatic project

1. Create or select one Chromatic project for `packages/react` in the demo organization.
2. Connect the GitHub repository and install the Chromatic GitHub App.
3. Publish and accept a clean `main` build before SEs branch. Keep `main` passing throughout the
   cohort so baseline ancestry remains trustworthy.
4. Store `CHROMATIC_PROJECT_TOKEN` as a GitHub repository secret. Share it locally only through the
   team's approved secret manager; never paste it into course docs, chat transcripts, or source.
5. Give SEs the least role needed for the exercise. Read-only access is enough for core onboarding.
   Use Reviewer for assigned peer review and Developer only when technical-training learners must
   accept their own UI Test baselines.

## Cohort guardrails

- One SE, one namespaced Git branch, one corresponding Chromatic branch.
- SEs review only their own newest branch build unless they are assigned as a reviewer.
- Do not enable automatic acceptance on SE branches.
- Do not enable TurboSnap until the project has enough successful full builds and the SE can
  explain the dependency graph.
- Archive or delete stale course branches only after useful feedback and technical evidence have been
  captured in the team's normal system.

## Facilitator checkpoints

Check in after core onboarding Sessions 3, 5, and 7. Ask learners to explain the Storybook 10 decision,
grounded MCP value, and local-to-CI test story in their own words.

Review technical readiness after Days 5, 10, and 15. Let the SE operate the product and explain each
decision. Ask what the customer gains or risks. Do not grade either stage on memorized commands or a
specific note-taking format.
