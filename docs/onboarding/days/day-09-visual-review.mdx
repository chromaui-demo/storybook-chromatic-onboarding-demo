## Plan your session

- 15 minutes: read
- 15 minutes: create controlled changes
- 30–45 minutes: review and recover
- 10 minutes: explain

## Separate UI Tests from UI Review

- [Visual testing](https://www.chromatic.com/docs/visual/)
- [UI Review](https://www.chromatic.com/docs/review/)
- [Branches and baselines](https://www.chromatic.com/docs/branching-and-baselines/)

UI Tests compare snapshots with accepted baselines for that story, mode, and branch. UI Review helps
stakeholders review the PR changeset against its merge base. They are related but not interchangeable.

## Create one intended change and one regression

1. Make one intentional UI change to `ReservationCard`, such as a reviewed spacing or badge treatment.
2. Add one accidental regression, such as clipped long text, a missing focus indicator, or a broken
   compact layout. Keep the two changes visually distinguishable.
3. Commit and publish a new Chromatic build.
4. In UI Tests, inspect baseline, new, and diff views. Accept the intended change and deny the
   regression. Add concise review comments that explain impact, not just pixel count.
5. Observe the build result after the denial. Fix the regression in code, commit, and publish again.
6. Verify the latest build compares against the expected accepted baseline and passes. Only the newest
   build on a branch should be treated as the review target.
7. Open UI Review for the branch or pull request and explain how its purpose differs from baseline
   maintenance.

## Record the evidence

Record links or screenshots for the initial diff, the denial, and the passing rebuild. In your progress
file, answer:

- What changed when you accepted the intended snapshot?
- What remained unchanged when you denied the regression?
- Which ancestor supplied the baseline?

## Demo the decision, not the pixel count

Demonstrate an intentional change and a regression without claiming that Chromatic decides whether
the UI is correct. Chromatic surfaces change; a reviewer supplies intent and judgment.
