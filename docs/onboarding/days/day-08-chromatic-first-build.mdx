## Give yourself 90 minutes

- 15 minutes: read and confirm access
- 20 minutes: configure the CLI
- 20–35 minutes: publish and inspect
- 10 minutes: explain and record

## Why Chromatic now?

By Day 7, the React Storybook can make important states reproducible and test them locally. That is a
real improvement, but it still leaves several questions unanswered: Which build should a reviewer
open? What changed on this branch? Is the change intentional? Which decision should block the merge?

Chromatic adds the shared, persistent, Git-aware half of the workflow. It publishes the same stories,
captures their rendered output, compares it with accepted history, and gives the team one place to
inspect evidence and record a decision.

Before touching the CLI, answer this in your progress file:

> What can Trailhead Travel do after this build that it could not do when Storybook only ran on a
> developer's laptop?

A useful answer names a person, a decision, and the evidence that person can now inspect.

## Check the shared project first

The facilitator must have connected one shared project, seeded a passing `main` build, and provided
the token through the approved secret manager. If `main` has no accepted build, stop and ask for that
foundation; branch comparisons are only useful with trustworthy ancestry.

## Publish from your branch

1. Install the Chromatic CLI in the React workspace and add a `"chromatic": "chromatic"` script to
   `packages/react/package.json`:

   ```sh
   pnpm --filter @demo/react add -D chromatic
   ```

   Create `packages/react/chromatic.config.json` with the official schema and the shared project's
   public `projectId`. Set `storybookBaseDir` to `packages/react` (relative to the repository root) and
   `storybookConfigDir` to `.storybook` (relative to the React workspace where the CLI runs). Do not
   put the project token in this file and do not enable `onlyChanged` yet.

2. Export `CHROMATIC_PROJECT_TOKEN` in your current shell from the team's secret manager. Do not place
   its value in shell history, `package.json`, the config file, your progress file, or a screenshot.
3. Confirm your Git branch is `onboarding/<handle>`, your working tree is committed, and it descends
   from the latest passing `main`.
4. Run `pnpm --filter @demo/react chromatic`. Let Chromatic invoke the React package's
   `build-storybook` script so you experience the same production path CI will use.
5. Open the build. Locate its Git commit and branch, Storybook URL, UI Tests result, and accessibility
   result if the feature is enabled for the project.
6. Add the branch build URL to your progress file. Never add the token.

## Make sure Chromatic built what you think it built

- The build belongs to your personal branch and expected commit.
- The published Storybook contains the React stories, including MSW and interaction states.
- There are no external composed stories counted as React UI tests.
- `git grep` does not find the token value in tracked or untracked course files.

## Practice the baseline story

Explain what the first accepted build establishes, why each branch can have separate baselines, and
why a passing `main` build matters after merges. Then connect it back to the customer: a baseline is
not “the correct design.” It is accepted history that makes the next visual change visible enough for
a human to judge.

<details>
<summary>Recovery</summary>

If the build lands on the wrong branch or commit, do not accept changes. Verify Git state and the
provider integration before rebuilding. If the token appears in a tracked file or shared transcript,
stop, notify the owner, and rotate it.

</details>

```sh
git add packages/react/package.json packages/react/chromatic.config.json pnpm-lock.yaml progress/<handle>.md

```
