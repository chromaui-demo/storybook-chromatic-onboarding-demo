## Understand the migration boundary

- [Storybook 10 release](https://storybook.js.org/releases/10.0)
- [Migrate to Storybook 10](https://storybook.js.org/docs/releases/migration-guide)
- [Upgrade Storybook](https://storybook.js.org/docs/releases/upgrading)

Pay attention to Node requirements, ESM-only configuration, automigrations, aligned Storybook
package versions, and upgrading one major at a time.

Before you run a command, state the customer reason for the upgrade. Storybook 10 moves the package
ecosystem to ESM and reduces install size. The current 10.x platform also supports the testing and AI
workflows used later in this track. Do not attribute every current 10.x feature to the 10.0 release.

## Run the supported upgrade workflow

1. Inspect `.nvmrc`, `pnpm-workspace.yaml`, `packages/react/package.json`, and
   `packages/react/.storybook/main.ts`.
2. Run the pinned upgrade and health checks:

   ```sh
   pnpm dlx storybook@10.5.5 upgrade
   pnpm --filter @demo/react exec storybook doctor
   pnpm --filter @demo/react typecheck
   pnpm --filter @demo/react build-storybook
   ```

3. Review `git diff`. On the normal `main` starting point, the upgrade should make no dependency
   changes because the repository is already pinned to 10.5.5. Treat unexpected edits as something
   to understand, not something to accept automatically.
4. Start `pnpm --filter @demo/react storybook`, open the React Storybook, and exercise Controls,
   Docs, viewport, and the Interactions panel.
5. Compare the verification steps with the customer's highest-risk runtime, addon, and framework
   boundaries.

If your facilitator supplied `course/storybook-9-start`, branch from that tag instead and follow the
migration guide's major-by-major path. Capture the dependency/config diff before continuing.

## Confirm the result

- `doctor`, type checking, and the static build pass.
- The React Storybook renders at its local URL.
- You can identify at least three upgrade risks and explain how you verified them.

## Questions to think through

- Which current constraint makes the upgrade worth the effort?
- Which migration risk would you test first for this customer?
- What would an automigration fail to prove?
- Which result would make you stop the rollout?

Imagine this comes up on a customer call: **How do we upgrade without treating the automigration as a
