## Make Storybook Test automatic

1. Inspect `.github/workflows/storybook-test.yml` and run `pnpm test:storybook` locally.
2. Confirm that the workflow installs dependencies, uses a Playwright browser environment, and runs
   the same command for pull requests.
3. Push your branch. Trace a render or interaction test from the story to the CI result.
4. Introduce one temporary failure on a disposable commit. Confirm that CI reports the exact story,
   then restore the test and push a passing commit.
5. Explain the adoption value: every pull request gets the same component-level proof without relying
   on a developer to run the test manually.

## Connect functional and visual CI

Inspect the repository's Chromatic workflow. If the facilitator has not added a React workflow yet,
create `.github/workflows/chromatic.yml` with:

- checkout using `fetch-depth: 0`;
- Node and pnpm versions from the repository;
- `pnpm install --frozen-lockfile`;
- the token from `${{ secrets.CHROMATIC_PROJECT_TOKEN }}`;
- `workingDir: packages/react`;
- a `push` trigger for `main` and SE branches.

Do not enable automatic acceptance, `exitZeroOnChanges`, or TurboSnap for SE branches. Push your
branch and trace the Chromatic build, UI Tests, and UI Review checks from commit to result.

Ask the facilitator before changing branch protection or required checks. Reading and explaining
policy is part of this day; changing repository-wide policy is not.

## Lead the five-minute demo

1. State the customer problem in the language of your chosen call.
2. Show an editable React story and its Autodocs.
3. Switch among deterministic MSW states.
4. Run an interaction and accessibility test.
5. Show the passing Storybook Test check and explain how the team returns to the failing story.
6. Open a Chromatic diff, explain the baseline, and distinguish visual from functional evidence.
7. Close with the coverage gap, the smallest adoption change, and the evidence that would show it helped.

## Verify the handoff from Git to Chromatic

- Storybook Test runs the same browser tests locally and in CI.
- The Chromatic workflow uses full Git history and a repository secret.
- The branch build is attached to the expected commit and surfaces its checks.
- You can explain which customer conversation you practiced and which improvement would make the demo
  more useful.

## Questions to think through

- Which check should block a pull request, and why?
- How does a developer return from CI to the failing story?
- Who owns a denied visual change?
- Which Git-history mistake could make the baseline misleading?

## How would you respond?

Be ready when someone asks: **Why do we recommend building `main`, and why are push-based workflows
often safer for baseline ancestry than default pull-request merge commits?**
