## Separate released facts from roadmap

- [Storybook feature lifecycle](https://storybook.js.org/docs/10.5/releases/feature-lifecycle)
- [Storybook roadmap](https://storybook.js.org/docs/10.5/releases/roadmap)
- Revisit the [Storybook 10 migration guide](https://storybook.js.org/docs/10.5/releases/migration-guide)

Use released documentation as the source of truth. Do not promise Storybook 11 dates, APIs, or framework
support that the project has not published.

## Inventory the version-specific work

1. Think through a short decision note in your preferred system with three sections:
   - stable practice to preserve;
   - Storybook 10.5 preview/version-specific detail;
   - verification required before Storybook 11 adoption.
2. Include CSF stories, args, play functions, deterministic mocks, accessibility intent, visual
   baselines, manifests, MCP, agentic setup, and multi-framework composition.
3. Inspect one non-React package and compare its Storybook config and stories with `packages/react`.
   Identify concepts that already transfer and AI/manifest capabilities that should not be claimed as
   equivalent in 10.5.
4. Run `storybook doctor`, type checking, and a static build again. Identify the repeatable commands
   that belong in any future major-upgrade pull request.
5. Draft a five-sentence customer answer to this question: **Should we wait for Storybook 11 before
   improving our component workflow?**

## Draft the customer note

- Every future-looking statement is either linked to released official guidance or explicitly labeled
  as an unknown to verify.
- The note separates framework-neutral habits from current React/Vite-only AI support.
- The selected non-React Storybook still builds independently.

## Questions to think through

- Which practices should survive any major upgrade?
- Which claims depend on a preview capability?
- Which framework differences need fresh verification?
- What would justify waiting, and what can the customer improve now?

## How would you respond?

Lead with durable outcomes: isolated states, deterministic tests, accessible behavior, reviewable
visual change, and discoverable catalogs. Then identify current preview boundaries plainly.

## Keep the readiness note useful

Store the note where the team will revisit it during upgrade planning. Do not commit a course-only file
unless repository documentation is the team's normal source of truth.
