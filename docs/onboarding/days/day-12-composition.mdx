## Understand the composition model

- [Storybook composition](https://storybook.js.org/docs/10.5/sharing/storybook-composition)
- [Chromatic composition](https://www.chromatic.com/docs/composition/)
- [Chromatic monorepos](https://www.chromatic.com/docs/monorepos/)

## Use the catalog as a customer sees it

1. Inspect `packages/hub/.storybook/main.ts` and `scripts/dev.mjs`. Draw the relationship among the
   hub, React, Next.js, Angular, Web Components, and React Native Web Storybooks.
2. Run `pnpm dev`. In the hub, open a story from every framework, then open each child Storybook
   directly. Observe which addons and toolbar state belong to the host versus the referenced catalog.
3. Stop one child Storybook. Describe how the failure appears in the hub and how you would diagnose it.
   Restart it and verify recovery.
4. Build the hub once with one child URL supplied through its documented environment variable. Use a
   local or approved published URL; do not invent a production endpoint.
5. Compare the React Chromatic test count before and after composition. Confirm externally referenced
   stories are browsable but are not captured as React project UI Tests.

## Verify the ownership boundaries

- All five references load in the hub and independently.
- You can identify the ownership, deployment, and test boundary for each catalog.
- You can explain why one-project composition is not the same as independently testing five projects.

## Questions to think through

- Which teams need one catalog, and which teams need separate ownership?
- What should happen when one referenced Storybook is unavailable?
- Which settings belong to the hub, and which belong to the child Storybook?
- How many Chromatic projects match the ownership model?

## How would you respond?

Give a three-minute architecture explanation for a platform lead choosing between one combined
Storybook and independently published Storybooks composed for discovery.
