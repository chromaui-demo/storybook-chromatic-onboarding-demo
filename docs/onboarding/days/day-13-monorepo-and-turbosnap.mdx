## Confirm that the project is ready

Do not enable TurboSnap just to finish the exercise. Confirm the shared project is eligible, has a
trustworthy sequence of full builds, and the facilitator approves the change. If not, perform the audit
and write the proposed config without publishing it.

## Trace controlled changes through the graph

1. From the repository root, inspect the Turbo task graph, package imports, React Storybook base
   directory, config directory, static directories, global preview imports, and shared
   `config/responsive.ts` dependency.
2. Run the TurboSnap helper in analysis mode using the current official CLI instructions. Review every
   proposed external or untraced path; never mark a file untraced just because it causes a full build.
3. With approval, set `onlyChanged: true` in `packages/react/chromatic.config.json`, retaining
   explicit `storybookBaseDir` and `storybookConfigDir` paths.
4. Publish three controlled builds, one change at a time:
   - a change inside `ReservationCard.tsx`;
   - a change to its story only;
   - a change to shared preview, theme, or responsive configuration.
5. For each build, predict the affected stories before opening Chromatic. Compare prediction with the
   changed-story result and record any full-build reason.
6. Revert the controlled changes you do not want to keep. Preserve the validated configuration only
   if the results were trustworthy.

## Test the risky boundaries

- Component and story changes retest the expected stories.
- Shared rendering/config changes do not incorrectly skip affected stories.
- Git history is complete in CI.
- Every `externals` or `untraced` entry has a written safety rationale.

## Practice the SE answer

If you cannot answer this yet, keep digging: **How does TurboSnap decide what changed, and why is a
fast but incomplete build worse than a slower full build?**
