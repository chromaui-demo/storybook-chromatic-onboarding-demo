## Turn one component into useful evidence

1. Add useful JSDoc to `ReservationCard`, its props, and the story meta. Explain intended use, not what
   the TypeScript syntax already says.
2. Add two meaningful story states. Choose states a travel product would need, such as sold out,
   maximum guests, a very long property name, or a localized price. Keep state in args whenever
   possible.
3. Give each story a short description that explains why the case exists.
4. Run the React Storybook and inspect:
   - the generated Docs page;
   - Controls and inferred prop types;
   - `/manifests/components.html`;
   - `/manifests/components.json`.
5. Remove `ai-generated` only from stories you personally reviewed and verified. Use `!manifest` for
   anything intentionally unsuitable for agent consumption, and explain that decision to a teammate or
   in your preferred notes.

Do not write application code that consumes the manifest JSON. Storybook 10.5 manifests are preview
APIs; verify their usefulness through the user-facing tools instead of depending on their schema.

## Check the human and agent views

- The new stories appear in navigation and render independently.
- Autodocs communicates component intent and prop meaning.
- The components manifest includes the reviewed stories and useful prop information.
- React type checking, story tests, and the static build pass.

## Questions to think through

- Which states carry real customer risk?
- What should the story name tell a developer or agent?
- Which prop description changes how someone uses the component?
- When should a story stay out of an agent manifest?

## How would you respond?

> “Why should we spend time improving stories and documentation if the component already works?”

Show one story in Canvas, Docs, and the manifest debugger. Explain why the same source improves
development, documentation, testing, and AI grounding.

over custom render functions so consumers can explore the state through Controls.
